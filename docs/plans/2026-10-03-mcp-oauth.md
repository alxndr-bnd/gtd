# MCP phase 2: OAuth 2.1 for claude.ai connectors

2026-10-03 · design note · task [SERBITO-375](https://serbito.atlassian.net/browse/SERBITO-375) ·
full plan: `docs/plans/2026-10-02-mcp-plan.md` (branch `plan/mcp`)

## Goal

A user adds gtd as a custom connector on claude.ai (web, desktop, mobile) and signs in with Google, email or
Telegram. No token copy-paste. Decision it changes: whether MCP access reaches people who never open a terminal.

**Hypothesis:** most users who want AI access use claude.ai, not Claude Code. Refuted if, 4 weeks after release,
OAuth connections are fewer than personal tokens.

## Phase 1 (done) — what phase 2 builds on

- `/mcp`: Streamable HTTP, stateless, JSON responses, official `mcp` SDK 2.x (`mcp_server.py`).
- Auth: `Authorization: Bearer gtd_…` → `api_tokens` (SHA-256, `last_used`), rate limit per token.
- Tools take `uid` from the token only.

Phase 2 adds a second token type. Tools and the transport do not change.

## What Claude expects (MCP authorization spec)

1. `/mcp` without a token → `401` with
   `WWW-Authenticate: Bearer resource_metadata="https://gtd.serbito.rs/.well-known/oauth-protected-resource/mcp"`.
2. Protected Resource Metadata (RFC 9728) at that URL (and at `/.well-known/oauth-protected-resource`):
   `resource`, `authorization_servers: ["https://gtd.serbito.rs"]`, `scopes_supported: ["tasks"]`.
3. Authorization Server Metadata (RFC 8414) at `/.well-known/oauth-authorization-server`: `issuer`,
   `authorization_endpoint`, `token_endpoint`, `registration_endpoint`, `revocation_endpoint`,
   `code_challenge_methods_supported: ["S256"]`, `grant_types_supported: ["authorization_code","refresh_token"]`,
   `token_endpoint_auth_methods_supported: ["none"]`.
4. Dynamic Client Registration (RFC 7591) at `POST /register`. Claude registers itself with redirect URI
   `https://claude.ai/api/mcp/auth_callback` (also accept `https://claude.com/api/mcp/auth_callback`).
   Client ID Metadata Documents (CIMD) are the newer option; support DCR first, add CIMD when Claude prefers it.
5. Authorization code + PKCE (S256 only), `resource` parameter (RFC 8707) equal to `https://gtd.serbito.rs/mcp`.
6. Access token audience = that resource. Refresh tokens rotate on every use.

## Design

| Piece | Decision |
| --- | --- |
| Authorization server | gtd itself. Google is only one of the sign-in methods on `/authorize`, so all three methods work. |
| `/authorize` | Not signed in → the existing sign-in screen, then back. Signed in → consent page: client name, redirect host, scope `tasks`, buttons Allow / Deny (POST, same-origin `Guard`). |
| Tables | `oauth_clients` (client_id, name, redirect_uris, created, last_used); `oauth_codes` (hash, client, uid, PKCE challenge, resource, expires 10 min, one use); `oauth_grants` (id, uid, client, created, last_used); access and refresh tokens as SHA-256 in `api_tokens` with `kind`, `grant_id`, `expires`. |
| Token format | Opaque random strings, like phase 1. Prefix `gtdo_` (access, 1 h) and `gtdr_` (refresh, 90 days, rotated). No JWT: one database, revocation must be instant. |
| `/mcp` auth | `api_token_user()` accepts both kinds; OAuth tokens must not be expired and must have the `/mcp` resource. Same rate limit. |
| Revocation | `POST /revoke` (RFC 7009) for clients. In “👤 Account”: a list of connected apps (“Claude”, last used) with **Disconnect** — deletes the grant and its tokens. |
| SDK | Use the SDK only for metadata models where it helps. Our own routes for `/authorize` (needs our sign-in and consent UI), `/token`, `/register`: `OAuthAuthorizationServerProvider` + `create_auth_routes` assume their own login flow and a per-app lifespan. Re-check this in SDK 3.x. |
| Guard | Exempt `/.well-known/*`, `/register`, `/token`, `/revoke` from the same-origin check (server-to-server calls). Keep `/authorize` POST same-origin. Add CORS `*` only to the `.well-known` documents. |
| Limits | `/register`: 10 per IP per hour; `/token`: 30 per client per minute; clients unused for 90 days are deleted. |

## Security checks

- Exact redirect URI match; no wildcards. Unknown `client_id` → error page, never a redirect.
- `state` passes through unchanged; codes are single use, bound to client, PKCE verifier and resource.
- Consent is required for every new client; the page shows the redirect host (phishing defence).
- Refresh token reuse → revoke the whole grant (theft signal).
- Never log codes or tokens (`ScrubQuery` already filters `code=` and `token=` in URLs).

## Tests (`tests/test_oauth.py`)

Metadata documents; 401 challenge header; DCR validation (bad redirect URIs); full flow with PKCE through
TestClient (register → authorize → consent → token → `/mcp` call → refresh → revoke); wrong verifier, reused code,
expired code, wrong resource; disconnect in “Account”; cross-user isolation with OAuth tokens; limits.

## Rollout

1. Release behind the existing deploy, test with a claude.ai custom connector on a staging account.
2. CHANGELOG EN/RU; README section “Connect claude.ai”.
3. Measure: connections by kind (`api_tokens.kind`), weekly active MCP users (`activity.channel = 'mcp'`).

## Open questions

- Scopes: one `tasks` scope now; split into read / write if users ask for read-only assistants.
- Self-hosted copies: issuer = `BASE_URL`; works without extra config.
